# 併發搶位壓力測試報告：加鎖前後的真實數據

**目的**：用 k6 對 `POST /api/v1/bookings` 做真正的併發壓力測試，驗證 `BookingService::book()` 的 `lockForUpdate()` 是否真的能防止超賣，並且量化這個鎖對吞吐量（QPS）造成多少影響。

**結論先講**：拿掉鎖之後，300 個並發請求對一個只有 20 個名額的時段會超賣到 42～45 筆；加回鎖之後連續多次測試都精準地卡在 20 筆，一筆不多。而且吞吐量幾乎沒有差——加鎖前後的 QPS 落在同一個區間（約 140～168 req/s），代表這個鎖的成本主要是「讓資料庫排隊處理同一列」，不是額外拖慢整個系統。

## 測試環境與方法

- **應用伺服器**：`php artisan serve --no-reload`，設定 `PHP_CLI_SERVER_WORKERS=32`，讓 PHP 內建伺服器 fork 32 個真正並行的 worker process（而不是預設的單一 process 依序處理）——這點很關鍵，若不開多 worker，伺服器本身就會把請求序列化，測不出資料庫層級的競速問題
- **資料庫**：真實 MySQL（MariaDB 10.11），不是 sqlite——sqlite 沒有真正的 row-level lock，測不出這個問題
- **壓測工具**：[k6](https://k6.io) v0.54.0，`per-vu-iterations` executor，每個虛擬使用者（VU）各自帶一組獨立的 Sanctum token，同時對同一個 `time_slot_id` 各發一次 `POST /api/v1/bookings`
- **測試腳本**：見 `docs/load-test/booking-race.js`（k6 腳本）與 `docs/load-test/seed.php`（灌測試資料：N 個使用者 + 1 個指定容量的時段）
- **對照組**：暫時把 `BookingService::book()` 裡的 `TimeSlot::whereKey(...)->lockForUpdate()` 改成不帶鎖的 `TimeSlot::whereKey(...)`，其餘邏輯完全不變（純粹的 read-then-write race，不是刻意寫爛的極端案例）——這個「不安全版本」只存在於這次測試過程中，從未進入正式程式碼

## 場景一：300 併發 / 容量 20

| 版本 | 執行次數 | 成功預約數（實際 `bookings` 筆數 / `time_slots.booked_count`） | 超賣 | 吞吐量 (req/s) | p95 延遲 |
|---|---|---|---|---|---|
| **未加鎖** | Run 1 | 42 | +22（超賣 110%） | 139.3 | 1.75s |
| **未加鎖** | Run 2 | 45 | +25（超賣 125%） | 168.0 | — |
| **未加鎖** | Run 3 | 44 | +24（超賣 120%） | 161.3 | — |
| **已加鎖** | Run 1 | 20 | 0 | 156.9 | 1.61s |
| **已加鎖** | Run 2 | 20 | 0 | 156.7 | 1.69s |
| **已加鎖** | Run 3 | 20 | 0 | 161.7 | 1.51s |

三次「未加鎖」測試，每次都超賣，且超賣數量並不固定（42/45/44）——這正是競速條件的典型特徵：結果取決於請求抵達與 MySQL 處理的時間交錯，不可預測、不可重現。三次「已加鎖」測試則精準地卡在 20，一筆不差。

## 場景二：1000 併發 / 容量 50（放大規模再驗證一次）

| 版本 | 成功預約數 | 超賣 | 吞吐量 (req/s) | p95 延遲 |
|---|---|---|---|---|
| 未加鎖 | 73 | +23（超賣 46%） | 151.5 | 5.44s |
| 已加鎖 | 50 | 0 | 164.1 | 5.02s |

規模放大到 1000 個並發請求、50 個名額，結論不變：未加鎖版本超賣 46%，加鎖版本精準卡在 50。

## 加鎖的吞吐量成本：幾乎為零

把六次 300-並發測試的 QPS 平均起來：

- 未加鎖平均：**156.2 req/s**
- 已加鎖平均：**158.4 req/s**

兩者落在誤差範圍內，加鎖版本甚至略高（測試環境雜訊，非統計顯著差異）。換句話說，`lockForUpdate()` 並沒有讓系統變慢——它做的事情是「讓同一個時段的並發請求在資料庫層級排隊處理」，而這個排隊本來就是保證資料正確性的必要代價，不是額外的效能稅。p95 延遲會隨並發數與名額數增加（因為同一時段的請求要排隊等鎖釋放），這是預期中的行為：**正確性換來的是延遲的重新分配，不是吞吐量的損失**。

## 為什麼吞吐量沒有明顯下降

這次測試的瓶頸本來就不是那把鎖，而是：

1. PHP 內建開發伺服器本身的請求分派開銷（`http_req_blocked`/`http_req_connecting` 就佔了不少時間）
2. 同一個時段的 `UPDATE time_slots ... WHERE id = ?` 本來就會被 InnoDB 序列化（即使沒有顯式 `lockForUpdate()`，寫入同一列的多個 transaction 在 commit 前也會互相等待），未加鎖版本省下的只是「先讀後判斷」那段本來就很快的邏輯
3. 換句話說，`lockForUpdate()` 換來的正確性幾乎是「免費」的，因為底層資料庫寫入本來就無法真正平行處理同一列

## 測試方法的限制

- `php artisan serve` 是開發用伺服器，不是正式環境會用的 PHP-FPM + Nginx 組合，因此**絕對吞吐量數字**（~150-165 req/s）不能直接當作正式環境的效能基準；但**加鎖前後使用同一套環境、只改一行程式碼**，兩者的相對比較是有效的
- 測試對象是單一時段的「熱點搶位」（worst case），不是一般均勻分散在多個時段的正常流量；這正是併發控制最需要被驗證的情境
- Rate Limiting（`throttle:booking`，每人每分鐘 5 次）在這次測試中不影響結果，因為每個虛擬使用者只送出 1 次請求

## 如何重新執行

```bash
# 1. 啟動一個獨立的測試用 MySQL，跑過 migration
# 2. 需要 k6：https://k6.io/docs/get-started/installation/
cd docs/load-test
php seed.php <capacity> <user_count>     # 灌測試資料，輸出 scenario.json
k6 run booking-race.js                    # 對目前的 BookingService 跑壓測
```

若要重現「未加鎖」的對照組，暫時把 `app/Services/BookingService.php` 裡 `book()` 方法的 `->lockForUpdate()` 移除，重新跑一次即可比較；測試完記得改回來（正式程式碼永遠不該移除這把鎖）。
